ENTRY G01-004 — 2026-08-14 — KILLER-FEATURE ROUTING / PRODUCT POSITIONING
================================================================================

Graphium positioning frozen from the target-user findings:
  FAST + SIMPLE + SAFE + NATIVE GTK

Killer features / differentiators, in priority order:

0. PERFORMANCE / PERCEIVED IMMEDIACY
   Speed is an admission condition, not a decorative feature. If Graphium feels
   materially slower than the lightweight-editor class, the rest of the feature
   advantage will not persuade the core Leafpad/L3afpad audience.

1. TRANSPARENT STRONG FILE SAFETY
   Preserve a small UI while adding mature behavior behind it:
     strong accepted file identity;
     changed/replaced/deleted-file awareness;
     guarded and atomic writes;
     savepoint-aware Saved/Modified state;
     alias/topology/race protection;
     no silent overwrite after external mutation.
   Safety should be mostly invisible until it prevents data loss.

2. ENCODING / BOM / EOL CLARITY
   Status/Properties should make the active representation understandable without
   forcing technical details into dialogs. Preserve representation safely and allow
   bounded explicit conversion later if authorized.

3. PERSISTENT ESSENTIAL PREFERENCES
   Graphium must remember user choices such as wrap, font, line numbers, status bar,
   tab width/spaces-tabs, appearance and useful window geometry. Minimalism does not
   mean forcing repetitive setup at every launch.

4. MATURE PRINT WORKFLOW
   Print / Print Preview / Page Setup belong to the serious desktop-editor experience.
   They must not enlarge the startup critical path.

5. COMPACT HIGH-VALUE STATUS
   Line/column, word/character count, encoding, EOL and Saved/Modified state provide
   concrete utility with very little UI surface.

6. MODERN APPEARANCE WITHOUT THEME BLOAT
   System / Light / Dark is retained. No theme marketplace/editor or cosmetic platform.

7. SAVE A COPY / SAVE VERSION COPY
   Distinctive safety/workflow value inherited from Calamus without rebinding the active
   document or polluting the simple one-file mental model.

Explicit competitive REJECT decisions remain:
  syntax highlighting in v1;
  tabs / multi-document window;
  IDE subsystems;
  project/workspace/file-browser systems;
  plugin platform.

Reason:
  Graphium should not become a smaller Geany/Kate or chase the Mousepad code-editor
  segment. Its value is mature plain-text editing with unusually strong safety.

ENTRY G04-004 — 2026-08-14 — CONFIRMATION-BIAS COUNTERMEASURE / DEEP MATURE-SOURCE REAUDIT
================================================================================

User correctly challenged the earlier audit as too shallow / potentially confirmation-biased.
G04 methodology is therefore tightened permanently.

CONFIRMATION-BIAS COUNTERMEASURE
--------------------------------
For every source comparison, record:
  1. Graphium assumption under test;
  2. mature evidence that contradicts or stresses it;
  3. materially different mature model and why it works;
  4. Graphium decision that would change if that evidence is stronger;
  5. ADOPT / ADAPT / REJECT / DEFER outcome.

An audit containing only evidence consistent with the pre-existing Graphium idea is invalid.
No new desktop candidate is issued until the whole discovered failure/design class is audited,
repaired and fully revalidated non-desktop.

Direct mature sources used for the rebuilt G04 include:
  Leafpad
  L3afpad
  Airpad
  Janus
  Mousepad 0.7.0
  Parchment
  gedit
  GNOME Text Editor
  NEdit
  JOE 4.8
  Lite XL
  published Calamus W116 where provenance is relevant

Key contradictory findings:

A. NATIVE UNDO STORAGE / GROUPING
  Earlier Graphium assumption:
    full-text G02 snapshots plus a fixed native idle/commit delay were a sufficiently simple
    quick-edit integration.

  Contradictory mature evidence:
    Leafpad/L3afpad record insert/delete deltas and coalesce structurally/key-contiguously;
    Airpad has explicit delta records and structural sequence logic;
    gedit/GNOME Text Editor/Mousepad use Gtk text/source buffer user-action boundaries for
    compound edits; NEdit and JOE use delta records, structural/contiguous grouping and
    bounded undo memory.

  Decision:
    ADAPT the common principle, not one implementation. G04 active GTK history becomes
    delta-based; `begin-user-action` / `end-user-action` and edit structure are semantic
    evidence; wall-clock time is not an Undo authority. G02 monotonic state-ID/savepoint
    semantics are preserved independently from native undo storage.

B. LARGE-DOCUMENT BEHAVIOR
  Earlier Graphium assumption:
    disabling multi-snapshot Undo above the G02 750,000-character threshold was acceptable
    safe degradation for the quick-edit target.

  Contradictory mature evidence:
    the directly inspected lightweight/mature editors store changed ranges/deltas rather than
    duplicating the complete base document per edit. A ~1 MiB text file is not exceptional
    enough to justify losing normal Undo in the target category.

  Decision:
    REJECT document-size-as-Undo-disable-switch for active G04. A 1 MiB document with one
    inserted character must keep Undo while storing one changed character of journal payload.

C. PROCESS / WINDOW TOPOLOGY
  Earlier Graphium assumption:
    one unique Gtk.Application reusing a window was a harmless implementation detail.

  Contradictory mature evidence:
    Leafpad/L3afpad naturally use independent processes/windows per invocation; Airpad
    explicitly sets G_APPLICATION_NON_UNIQUE and opens each additional command-line file in
    its own spawned process. Mousepad can disable its server but its tab/server complexity is
    intentionally outside Graphium's target.

  Decision:
    ADOPT the quick-edit topology: one invocation/process -> one window -> one document;
    Graphium is NON_UNIQUE. A second file-manager invocation cannot hijack the first document.
    Multi-file CLI input fans out one process per file.

D. PERFORMANCE ORACLE
  Earlier Graphium assumption:
    Graphium exact first-editable values could be compared to comparator first-window-mapped
    proxy values if clearly labelled.

  Contradictory mature evidence:
    Leafpad and L3afpad explicitly show the window before command-line file Open; Janus also
    shows before Open, while Airpad has a different order. FIRST_VISIBLE is therefore not
    FIRST_EDITABLE and structurally favors different startup orders.

  Decision:
    split metrics. Common FIRST_VISIBLE is measured externally by the same oracle for all four
    target products and is the only G04 cross-product ratio. Graphium exact FIRST_EDITABLE is
    a separate inherited-pipe measurement and is not compared numerically to FIRST_VISIBLE.
    G12 must establish one common external FIRST_EDITABLE oracle before hard editable-readiness
    competition claims.

E. READY SYNCHRONIZATION
  Earlier Graphium assumption:
    existence of a ready file could represent a completed readiness receipt.

  Contradictory systems fact exposed by the run:
    namespace existence and complete payload publication are different events.

  Decision:
    REJECT ready files. Graphium child emits one short complete READY record over an inherited
    pipe with one os.write; parent waits for newline and verifies emitter PID.

  6. conservative representation semantics for encoding/BOM/EOL.

  Leafpad
  L3afpad
  Mousepad
  FeatherPad

2026-08-14 — LIGHTWEIGHT BUDGET / MANDATORY ANTI-BLOAT GATE FOR EVERY Gxx
===============================================================================

Decision status:
  FROZEN PRODUCT/METHODOLOGY RULE
  APPLIES_TO=G05_AND_ALL_LATER_Gxx
  DOES_NOT_CHANGE_G04_PRODUCT_SCOPE=YES
  G04_STATUS=OPEN
  G05_STARTED=NO

Reason for this freeze:
  Menu Architecture R3 is a MAXIMUM V1 ENVELOPE, not an implementation checklist.
  A function being useful is not sufficient reason to add it. Every proposed
  capability must also justify its permanent cost in product state, runtime work,
  architecture, testing, Help, persistence and user mental model.

Core lightweight principle:
  Graphium remains lightweight when it gives the user the smallest coherent set
  of mature desktop-text-editor capabilities needed for normal quick editing,
  while refusing infrastructure whose main purpose is multi-document management,
  software development, project organization or extensibility.

  The controlling question for every visible command remains:

    DOES THIS HELP THE USER EDIT A NORMAL TEXT FILE
    FASTER, CLEARER OR MORE SAFELY?

  If the answer is YES, the feature is only a candidate for adoption. It must
  still pass the Lightweight Budget below.

LIGHTWEIGHT_BUDGET_MANDATORY_GATE=YES
MENU_ARCHITECTURE_R3_IS_MAXIMUM_ENVELOPE_NOT_CHECKLIST=YES
FEATURE_UTILITY_ALONE_IS_INSUFFICIENT=YES

Mandatory anti-bloat review for each future Gxx feature:

  1. USER VALUE
     - Is the capability directly useful to the primary quick-edit target?
     - Is the benefit frequent or important enough to justify permanent surface?
     - Does it improve speed, clarity or safety of ordinary text-file work?

  2. MENTAL-MODEL COST
     - Does it introduce a new concept the user must learn?
     - Can it reuse an existing File/Edit/Search/View/Document/Help concept?
     - Does it create overlapping commands or two ways to configure the same fact?

  3. PERSISTENT-STATE COST
     - Does it require new persistent state?
     - If yes, is that state small, explicit, filesystem-backed or ordinary config,
       and clearly owned by one authority?
     - New hidden databases, session stores or feature-specific registries are
       forbidden unless a later explicitly authorized work item proves necessity.

  4. BACKGROUND-WORK COST
     - Background activity is not justified merely by convenience.
     - No background analytics, document-wide polling or periodic rescans.
     - File monitoring, where required, remains event/interrupt driven and its
       event is never the truth authority.
     - Work that can be on-demand or lazy must remain on-demand or lazy.

  5. STARTUP-CRITICAL-PATH COST
     - Printing, Help, Statistics, monitoring maintenance and other nonessential
       subsystems must stay outside startup critical path unless proven otherwise.
     - No eager syntax/parser/analytics initialization.
     - Safety may not be weakened to improve benchmarks; performance may not be
       ignored merely because a feature is useful.

  6. ARCHITECTURAL COST
     - A marginal command does not justify a new subsystem, service graph,
       state machine or generalized framework.
     - Prefer a small direct implementation with one clear authority.
     - If a feature requires architecture that mainly exists to support itself,
       default decision is DEFER or REJECT.

  7. DUPLICATION COST
     - DIRECT_COMMAND_SETTING_DUPLICATION remains FORBIDDEN.
     - A persistent View setting controlled directly from View is not repeated in
       Preferences simply to expose a second route.
     - Diagnostic information belongs in Properties/About unless it is itself a
       normal workflow action.

  8. DOCUMENT-WIDE COMPUTATION COST
     - No mandatory eager whole-document analytics for status decoration.
     - Word/character statistics remain on-demand unless a later implementation
       proves incremental/cheap behavior under real performance gates.
     - Large-document and pathological-line safety remains part of qualification.

  9. STORAGE / RECOVERY COST
     - No session restoration or multi-document workspace state in v1.
     - Future crash recovery, if adopted at G13, uses a separate recovery cache and
       does not silently grant a background subsystem authority to Save the target.

  10. SCOPE-DRIFT CHECK
      The following remain outside the v1 identity and are not reintroduced by
      incremental convenience work:
        NO tabs
        NO named sessions
        NO workspace/project tree
        NO syntax/language engine
        NO column-editing platform
        NO plugin/extensibility platform
        NO IDE/LSP/debugger/terminal/Git subsystem
        NO multi-file search workflow
        NO binary/hex-editor identity
        NO theme marketplace / arbitrary styling platform

  11. HELP / TEST / MAINTENANCE COST
      - Every visible command must update Help/Keyboard Shortcuts in the same work
        item when applicable.
      - Every new persistent state requires regression coverage for defaults,
        persistence and failure behavior.
      - Every file-affecting feature must preserve strong identity, guarded Save,
        content neutrality and exact Saved/Modified semantics.

  12. REAL-DESKTOP COST
      - A feature that passes headless tests but makes the T480 shell noticeably
        slower, less responsive or visually more complex may still be rejected.
      - Performance and responsiveness qualification remains product behavior, not
        a cosmetic optimization.

Decision matrix required for each candidate feature:

  ADOPT
    High/clear target-user value; bounded state and runtime cost; no scope drift;
    no duplicated surface; passes safety/performance requirements.

  ADAPT
    Useful capability, but mature-source form is too large or stateful; Graphium
    implements a deliberately smaller form that preserves the user benefit.

  DEFER
    Useful but nonessential for the current v1, or its implementation cost cannot
    yet be shown to fit the Lightweight Budget.

  REJECT
    Primarily serves multi-document/code/project/extensibility workflows, creates
    disproportionate infrastructure, duplicates state/surface, weakens safety or
    performance, or changes Graphium's product category.

Current R3 examples under this rule:

  Toolbar
    DEFER to G06 audit. Presence in the maximum envelope is not authorization.

  Full Screen
    ADOPT only if implementation is near-zero architectural/runtime cost and does
    not create a separate Zen-mode subsystem.

  Statistics
    ADAPT as on-demand dialog. Mandatory live whole-document counting is not part
    of v1 without cheapness proof.

  Properties
    ADOPT as compact fact surface; REJECT inspector/debug-console expansion.

  Open Recent
    ADOPT as simple file history; REJECT session/workspace semantics.

  Save Version Copy
    ADOPT only as deterministic copy command; REJECT timeline/database/versioning
    subsystem growth.

  Encoding / Line Endings
    ADOPT as observation + explicit conversion; REJECT implicit Save conversion,
    broad codec/platform expansion for its own sake or content normalization.

  Preferences
    ADAPT as intentionally small. It owns only settings without a clearer direct
    command surface; it does not become a second copy of View/Document menus.

Lightweight closure criterion for each Gxx:

  A work item cannot be considered competitively closed merely because its tests
  pass. Its final audit must also record that the implemented delta remains within
  the Lightweight Budget and did not create hidden scope expansion.

  Required closing marker:

    LIGHTWEIGHT_BUDGET_GATE=PASS

  A PASS means, at minimum:
    startup critical path not unnecessarily expanded;
    no duplicate settings/command authority introduced;
    no new hidden persistent database/session state;
    no unjustified background work;
    no scope drift toward tabs/syntax/projects/plugins;
    no weakening of file-safety semantics;
    no accepted responsiveness regression without explicit product decision.
